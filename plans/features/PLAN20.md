# PLAN — Phase 20 (In-app help: every page can explain itself, and any page can walk you through itself)

> Nineteen phases built thirty-four pages. The only map is [docs/FEATURES.md](../../docs/FEATURES.md), 21 docs under `docs/`, and ⌘K, and **none of them are inside the app**. `docs/` is in [.dockerignore](../../.dockerignore), so a deployed instance cannot show them. Someone looking at `/plan/cashflow` and wondering what "low-water date" means has to leave the app, find the repository, and guess which of 593 lines in `CASHFLOW.md` has the answer.
>
> **This phase reverses a recorded decision, and says so.** [PLAN19.md](PLAN19.md) P19-34 declined *"an in-app tour, onboarding wizard, or tooltips"* and filed it under Open Items with the trigger *"Revisit only if a real second operator reports getting lost."* **The trigger is now met, in its strongest form: the owner asked for it (2026-10-11).** This follows the ADR-018 / ADR-030 / ADR-036 / ADR-039 / ADR-043 precedent: *the owner explicitly asked, so it's in scope*. P19-34's reasoning still applies to **how much** we build, though. Help is a feature, and features need a counterweight, so `personal-tool-builder` runs at the gate (P20-00).
>
> **The deliverable**: on any authenticated page, a **`?` button in the chrome** (also the `?` key, and a "Help: *this page*" result in ⌘K) opens a **help panel**. The panel says what the page is for, how to read it, and what its terms mean. Pages where the walkthrough is worth more than the text also get a **"Take the tour"** button, which highlights the page's real elements one at a time. Nothing is sent anywhere, nothing is tracked, and no number on any page changes.

---

## Hard boundaries (the phase's invariants)

1. **No figure moves.** Help is a layer *on top of* the pages and never a change to what they compute. Help text is **static**: it never puts the household's balances, names, or transactions into the copy. (This also means help content can never leak data, can be cached, and can be tested without a database.)
2. **Zero egress, zero telemetry.** No third-party help or onboarding SaaS: no Intercom, Pendo, Appcues, WalkMe, Userpilot, Chameleon, or HelpScout Beacon. All of them are analytics products underneath, and CLAUDE.md §Privacy rules them out. Tour completion, help opens, and "was this helpful?" are **never recorded or sent**. The only state is a per-device "seen this tour" flag (ADR-060).
3. **No AI help assistant.** Not hosted, and not local either. A "chat with the docs" bot is §Tier 2A/A territory in [SKILLS.md](SKILLS.md) and needs its own ADR. Recorded in Open Items so nobody sneaks it in as a "help feature".
4. **No new runtime dependency unless the gate approves it** (ADR-059 §3). The UI is hand-rolled Tailwind today, and a tour engine is roughly 300 lines of positioning and focus management.
5. **Still one user** (ADR-004 stands). Tours and help are per-device conveniences, not per-person profiles.

## What already exists (do not rebuild — extend these)

- **The nav manifest is the single source of truth for destinations** ([nav/manifest.ts](../../src/lib/nav/manifest.ts), ADR-035), with a coverage guard that fails when a page is missing. Help should copy that pattern: **one registry, plus a guard that fails when a page has no help entry**.
- **[docs/FEATURES.md](../../docs/FEATURES.md) already has one line per surface** (the question each page answers), and [nav/features-doc.test.ts](../../src/lib/nav/features-doc.test.ts) already contains `pageRoutes()`, which walks `src/app/**/page.tsx` and normalizes dynamic segments to `<id>`. **Move that helper into a shared test utility rather than copying it.** FEATURES.md's "question" column is the starting draft for every help entry's one-line summary.
- **`UNNAVIGATED_ROUTES`** (`["/login"]`) and FEATURES.md's `LISTED_BY_PARENT` already classify the routes that are steps inside a flow (import preview, Plaid map/progress, watchlist new/edit). The help registry reuses that classification: **flow steps get their own entry** (they are exactly where people get lost), and `/login` gets none (the nav does not render there).
- **The ⌘K palette** ([command-palette.tsx](../../src/components/command-palette.tsx)) is mounted once from [app-nav.tsx](../../src/components/app-nav.tsx), opens from a window event (`OPEN_COMMAND_PALETTE_EVENT`), and already has a pure, local "Pages" group ([search/pages.ts](../../src/lib/search/pages.ts)). Help should follow the same pattern: **mount it once in the chrome, open it from a window event, and add one local result group**. No pages are edited.
- **`AppNav` is a server component that renders on every authenticated page.** Mounting the help island there makes it available on all 33 authenticated routes **without touching a single `page.tsx`**. Tours are the exception: they need `data-tour` anchors on page elements (Batch 4).
- **The empty states already exist and should not be duplicated.** [first-run.tsx](../../src/components/dashboard/first-run.tsx) collapses the dashboard to "Add your first account." Help does not replace empty states. It explains a page that already has data.
- **`make seed-demo`** (P19-32) fills a fresh instance with a fictional household, so **every tour can be written and checked against a full page**, and any screenshot in the docs comes from synthetic data (PLAN_PRE_PUBLICATION's lesson).
- **Seven `privacy-egress.test.ts` suites** walk real module graphs and fail closed. `src/lib/help/` gets the eighth.
- **The first `.tsx` render test** landed at P19-10, and [vitest.config.ts](../../vitest.config.ts) already has `esbuild.jsx: "automatic"`. Render tests for the panel and the tour need no new setup.
- **Naming hazards.** `guidance` already means the deterministic advice engine (`src/lib/advice`, [guidance-disclaimer.tsx](../../src/components/guidance-disclaimer.tsx), [docs/GUIDANCE.md](../../docs/GUIDANCE.md)). `review` means the uncategorized queue. `instance` means the operator page. So the new module is **`src/lib/help/`**, the components are **`src/components/help/`**, and the anchor attribute is **`data-tour`**. **Nothing in this phase is called "guide", "guidance", or "review".**

## ADRs proposed at plan time

These are appended to [IDEAS.md](IDEAS.md) §11 as **ADR-058 → ADR-060**, gated by P20-00. The log runs to **ADR-057** today, but [PLAN_PRE_PUBLICATION.md](PLAN_PRE_PUBLICATION.md) is uncommitted and owns 055–057, so **re-check the maximum at commit time** (the P18-00 and P19-00 checks both *failed usefully*).

### ADR-058 — In-app help is in scope, as static, per-page, bundled content

1. Every authenticated page has a help entry. The `?` button, the `?` key, and ⌘K open it. This reverses PLAN19 P19-34's deferral, and that decision is **cited, not edited**.
2. Help content is **static**: it never interpolates household data (Hard boundary #1).
3. Help explains **what the page means**. It does not repeat the operator docs. `docs/*.md` stays the operator and deep-dive layer (deploy, Plaid setup, threat models). In-app help is the reader's layer: what am I looking at, how do I read it, what does this word mean, and what can I do here?
4. **Rejected**: third-party help SaaS (privacy); an AI help bot (needs a §Tier 2A ADR); serving `docs/*.md` in the app (see ADR-059 §2).

### ADR-059 — Help content is typed TypeScript data, not Markdown

1. Entries live in `src/lib/help/content/*.ts` as typed literals that satisfy a `HelpEntry` interface. The registry maps a **route pattern** (`/accounts/<id>/import`) to an entry, using the same `<id>` normalization as `features-doc.test.ts`.
2. **Why not render `docs/*.md`?** (a) `docs/` is dockerignored, so changing that ships the threat models and DEPLOY.md inside the image for no reader benefit. (b) Rendering Markdown means a new dependency **and** an HTML-injection surface (`dangerouslySetInnerHTML`), which `frontend-security-coder` would flag. (c) The docs are written for an operator, and help is written for someone reading the page. They are different texts.
3. **Body text is structured, not free HTML**: a small union of blocks (`paragraph`, `steps`, `definition`, `callout`) whose strings are rendered as React text nodes. Emphasis is a typed `{ strong: string }` span, not markup. **No `dangerouslySetInnerHTML` anywhere under `src/components/help/`**, and P20-31 asserts it.
4. **Hand-rolled tour engine, no library (proposed).** The candidates were `driver.js` (MIT, no dependencies, no telemetry, and the best of them), `react-joyride` (React 19 support lags), and Shepherd.js. The hand-rolled engine is about 300 lines, keeps one styling system, and gives us full control of focus. **If the owner prefers `driver.js` at the gate, that is a valid choice**: it passes through `dependency-management-deps-audit`, gets a THIRD_PARTY.md row, and is pinned exactly.
5. **Drift guards are mandatory and are the reason for using TypeScript.** Every page route has an entry. Every `relatedRoutes` link is a real `Route`, checked by typed routes. ~~Every `docRef` names a file that exists in `docs/`.~~ *(Dropped at the gate with the field: help never references `docs/`.)* **Every tour step's anchor exists as a `data-tour="…"` attribute somewhere under `src/`.** Help that describes a page that changed is worse than no help, so these guards are what make it maintainable.

### ADR-060 — Tour state is a per-device convenience in `localStorage`; no schema change

1. "Seen" and "dismissed" flags are stored in `localStorage` under `my-money:help:tour:<tourId>:v<version>`. **Bumping a tour's `version` offers it again** after the page changes enough to need it.
2. Every read and write is wrapped in `try/catch`. If storage is unavailable (a private window or blocked storage), the tour still works and is simply offered again. It is **never needed for correctness**.
3. **Why not a column on `household_profile`?** Per-device behavior fits this case: two household members on two phones should each be offered the tour. A database column would also mean a migration, a server action, and a write path just to remember a dismissed popover. **If the owner wants tour state to follow the login across devices, that becomes a nullable `jsonb` column on `household_profile`** (the singleton, so there is still one writer, as at P19-12). It is an alternative recorded at the gate, not the default.
4. **Auto-offer, never auto-start.** On the first visit to a page that has a tour, a small dismissible "New here? Take a 30-second tour" chip appears next to the `?` button. The tour itself **only ever starts from a click**. Dismissing the chip sets the flag. Nothing pops up over the page uninvited.

### Batch 4 — The tour engine

- **P20-13** — `src/lib/help/tour-plan.ts`: **pure** step resolution. Given a tour's steps and a predicate that says whether an anchor is present and visible, it returns the runnable steps. A step whose anchor is absent (an empty book, a collapsed section, or the section strip hidden below `sm:`) is **skipped, not broken**. If fewer than two steps survive, the tour is not offered. **Vitest**: skipping, ordering, the minimum-step rule, and the `version` key format. *Skills*: `test-driven-development`, `vitest-skill`.
